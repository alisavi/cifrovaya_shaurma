# Executor: аналитика привычек по наблюдательным данным

## Когда применять

Задача про анализ четырёх блоков признаков (питание, сон, стресс, физическая
активность) на наблюдательных данных, с очисткой, логистической регрессией,
permutation importance и отчётом. Работай только внутри каталога, указанного
в задании (например `works/w1-hab`).

## 0. Входы и стоп-условия

1. Прочитай `spec.md`, `data/PASSPORT.md` и `bundles/index.json`.
2. Данные получай только через `data/fetch.py` (или `data/fetch.sh`, если он
   описан в паспорте); исходники кладутся в `data/raw/`.
3. Паспорт обязан содержать:
   - ссылку на источник (URL или DOI);
   - лицензию (явное название, например CC BY 4.0);
   - `sha256` файла(ов) из `data/raw/`.
4. Проверь, что `sha256` в паспорте совпадает с фактическим хешем файла.
5. Если хотя бы одного из трёх пунктов нет, файла паспорта нет или нет самих
   данных — **остановись** и перечисли, чего не хватает. Не выдумывай ссылку,
   лицензию, хеш или данные.

## 1. Разметка блоков признаков

Составь таблицу соответствия «колонка → блок» до моделирования и сохрани её в
`out/feature_map.json`.

- **Питание**: калории/качество рациона, частота приёмов, овощи/фрукты, сахар,
  фастфуд, вода.
- **Сон**: длительность, качество, время засыпания/подъёма, нарушения.
- **Стресс**: шкалы стресса, тревожность, восстановление.
- **Активность**: шаги, минуты умеренной/интенсивной нагрузки, сидение,
  тренировки.
- **Контроль**: возраст, пол, раса, образование, курение. ИМТ — целевая
  переменная, а не контроль: иначе утечка.

Целевая переменная задаётся заданием/паспортом (например, бинарный исход
«высокий стресс» или «нарушение сна»). Зафиксируй её определение в
`out/metrics.json`.

## 2. Очистка (без заполнения средним)

- Приведи типы: числа — numeric, категории — category/string, даты — datetime.
- Удали точные дубликаты; при наличии ID — дубликаты по ID (оставь первую
  запись, зафиксируй число удалённых).
- Построй отчёт о пропусках по каждой колонке. **Не заполняй средним/медианой.**
  Допустимо: complete-case для модели, явная категория `unknown` для
  категориальных, исключение колонки при пропуске > 40 % (с обоснованием).
- Выбросы ищи robust z-score (MAD) и/или IQR; помечай, не удаляй автоматически.
  Удали только физически невозможные значения (отрицательный сон, шаги > 100k
  и т. п.) с указанием правил.
- Зафиксируй n до/после каждого шага в `out/metrics.json` → `cleaning`.

## 3. Моделирование

1. **Baseline**: константное предсказание (доля положительного класса) на
   train; метрики на test.
2. **Логистическая регрессия**: one-hot для категорий, стандартизация числовых
   (mean/SD по train), `class_weight="balanced"` при дисбалансе, stratify split,
   фиксированный `random_state` (например 42), 5-fold CV.
3. **Permutation importance** на test: 1000 перестановок, метрика ROC AUC,
   среднее и 95 % CI (2.5/97.5 перцентили).
4. Для коэффициентов — bootstrap 1000 ресэмплов, пересчёт на стандартизованных
   признаках; получи 95 % CI.

Метрики: ROC AUC, PR AUC, accuracy, balanced accuracy, log loss, Brier score —
для baseline и модели.

## 4. Факторы: направление, сила, 95 % CI

Для каждого фактора в `out/factors.csv`:

| колонка | смысл |
|---|---|
| `factor` | имя признака |
| `block` | питание / сон / стресс / активность / контроль |
| `n` | число наблюдений в модели |
| `coef_std` | стандартизованный коэффициент |
| `or_per_sd` | odds ratio на 1 SD |
| `ci_low`, `ci_high` | 95 % bootstrap CI для OR |
| `direction` | positive / negative / unclear (если CI включает 1) |
| `strength` | weak / moderate / strong по \|coef_std\| (<0.2 / 0.2–0.5 / >0.5) |
| `perm_importance` | среднее падение ROC AUC |
| `perm_ci_low`, `perm_ci_high` | 95 % CI permutation importance |
| `p_value` | по bootstrap SE (нормальное приближение); иначе пусто |

## 5. Выходные файлы

- `out/metrics.json` — паспортные данные источника, target, n, cleaning,
  baseline vs model, CV, seed, версии библиотек.
- `out/factors.csv` — таблица выше.
- `out/feature_map.json` — соответствие колонок блокам.
- `notebook.ipynb` — воспроизводимый ход анализа с комментариями «зачем»
  (14+ ячеек: паспорт, пропуски, target, baseline, Pipeline, importance,
  факторы, традиционный способ, ограничения).
- `data/fetch.py` (или `fetch.sh`) — загрузка исходников и печать sha256.
- `report/report.html` — яркая версия: вывод в заголовке, KPI, графики.
- `report/report_engineer.html` — инженерная версия: метаданные, β и 95% CI,
  плотные таблицы. Содержание то же, меняется подача.
- Оба отчёта содержат секции: 1) Источник и паспорт; 2) Данные и очистка;
  3) Признаки по блокам; 4) Методы; 5) Результаты baseline/модели;
  6) Факторы (таблица + график); 7) **«Традиционный способ»** — как задачу
  решали бы без ML: таблицы сопряжённости, стратификация, простые доли,
  ручные пороги, и чем это отличается от модели; 8) Ограничения;
  9) Выводы-гипотезы.
- `review/report.json` — результат checker.

## 6. Формулировки выводов

Данные наблюдательные. Запрещены формулировки «X вызывает Y», «влияет»,
«приводит к». Пиши «связан с», «ассоциирован», «гипотеза», «наблюдается
различие». Указывай смешение, обратную причинность, самоотчёт, отбор.

## 7. Checker

В конце вызови checker с рубрикой `shared/rubric/practice-v1.json`; он пишет
`review/report.json`. Оценку не выставляй — её ставит человек. Если checker
недоступен или рубрика отсутствует, зафиксируй это в отчёте и не подменяй
проверку самооценкой.
